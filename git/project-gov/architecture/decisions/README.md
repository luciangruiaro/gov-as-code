# Architectural decisions

An ADR records one decision the code must obey: its context, the options weighed, the laws it sets and how we know they hold. Write a new one from [`_template.md`](_template.md) with the `gov-adr` skill, starting from an entry in the [ADR backlog](backlog.md) or an answered question in an alignment worksheet (`resources/audits/*_prd-adr-alignment.md`).

## Rules
1. **ADRs are vision.** An ADR reads the same whether the system is 10% or 100% built: no sprints, no deadlines, no file:line evidence.
2. **Deviations live in the [register](../deviations/README.md), never in the ADR.** When code departs from a ratified ADR, add a row there. Never weaken the ADR to fit the code.
3. **Requirements by id.** Every ADR names the PRD requirement ids it rests on in its header (`**Requirements:**`), so a PRD change finds it.
4. **Supersede, don't rewrite.** To change a ratified decision, write a new ADR and fill in both `Supersedes` and `Superseded-by`.
5. **Files are `ADR-0NN-kebab-slug.md`.** Numbers come from the backlog and are never reused.
6. **Product repositories may keep their own ADRs** for local decisions, with a `Derives-from: <slug>-gov ADR-0NN` line when they refine one of these.

## Status vocabulary
| Status | Means | In an architecture review |
|---|---|---|
| `DRAFT` | Written, not yet ratified | Advisory notes only |
| `VISION-RATIFIED` | Ratified by the design authority (the solution architect); binds the code | Findings |
| `CLOSED-DONE` | Fully built and guarded by tests | Regression guard |
| `DEFERRED` | Parked, with the reason in the ADR | Nothing |

Lifecycle: backlog entry (`open` → `partial` → `decided`) → ADR `DRAFT` → `VISION-RATIFIED` → `CLOSED-DONE`, or `DEFERRED` at any point.
