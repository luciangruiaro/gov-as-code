# ADR-001 — Governance lives in code, beside the code

> **Status:** DRAFT · **Date:** 2026-01-05 · **Decided by:** solution architect · **Supersedes:** — · **Superseded-by:** —
> **Requirements:** — · **Backlog:** adr-001 · **Governs:** every repository in the workspace
> Deviations from this ADR are tracked in the [deviation register](../deviations/README.md), never here.

## 1. Context
We version the code that defines the software. The decisions, requirements, workflows and knowledge that shape it are often scattered instead: in documents, chats, call notes and people's heads. With mixed teams of people and coding agents, that knowledge has to be shared, versioned and readable by both. Otherwise each agent session, and each new team member, starts from nothing and guesses.

Not everything needs the same treatment. Live working material (decks, call transcripts, raw ideas, the client's Word documents) changes by the hour and must reach everyone at once. Agreed material (requirements, architectural decisions, plans, reviews) changes less often, and it matters that we can see how it changed and go back.

## 2. Options
| Option | For | Against |
|---|---|---|
| A shared drive only | Real-time, familiar, no tooling | No history worth the name, no diffs, nothing an agent can trust as current |
| A wiki | Searchable, linkable | Drifts from the code; changes are not reviewed; agents read it poorly |
| **A shared drive for live material plus a governance repository for agreed material** | Each kind of knowledge gets the right tool; Git gives history, diffs and review; the drive gives immediacy | Two places to learn; needs a map (`WORKSPACE.md`) and mirrors between them |

## 3. Decision: the laws
1. **Two halves, one map.** Live material lives on the shared drive. Agreed material lives in this governance repository. [`WORKSPACE.md`](../../WORKSPACE.md) says what lives where, and it is kept current.
2. **The client's documents stay theirs; Git keeps mirrors.** The master PRD stays in Word, and its Markdown mirror in `prd/` is regenerated by `prd/sync/sync.py`, never edited by hand. Backlog and in-app feedback are mirrored to the drive one way, by tools.
3. **Decisions are ADRs, and only ratified ADRs bind.** Code that departs from a ratified ADR is recorded in the deviation register. The ADR is never weakened to fit the code.
4. **Requirements are traced to decisions by id.** ADRs, the ADR backlog, questions and plans cite PRD requirement ids. A PRD change is reviewed against every decision that cites a changed id (`prd/sync/impact.py`, then an alignment worksheet).
5. **One rule set for people and agents.** [`AGENTS.md`](../../AGENTS.md) is canonical, and every agent tool reads it or a file that imports it. Shared skills live in `.agents/skills/`, independent of any one tool.
6. **Deterministic where possible, judgment where necessary.** Tools collect, convert, diff and index; people (and agents under their review) decide. A tool never edits a decision.

## 4. Acceptance criteria (timeless)
1. `py -3.12 -m unittest discover -s tests` passes: the agent files agree, every skill is listed, the generated indexes are current.
2. `py -3.12 prd/sync/sync.py --check` passes on the current master PRD.
3. Every ADR names the requirement ids it rests on, or `—` when it rests on none.
4. Every product repository's own agent file links to this repository and lists the ADRs it keeps.

## 5. Consequences
- Easier: onboarding (people and agents read the same map), audits (why did this change? `git log`), PRD changes (impact is computed, not remembered).
- Harder: discipline. Mirrors must be re-run, ADRs written, the map kept current. The skills and the daily digest carry most of that load.
- Accepted: some knowledge stays off-system (private conversations, the client's internal tools). `WORKSPACE.md` names those sources so nobody assumes they are covered.
