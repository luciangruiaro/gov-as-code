# Group & Commit

Take the current uncommitted local changes and land them as a clean
sequence of small, logical commits. One concern per commit. No push.

## Portability

Tool names are Claude Code's. Elsewhere use the equivalent and keep every gate. AskUserQuestion: ask in chat and wait. Explore agents: subagents, else sequential reads. Worktree isolation: `git worktree add`. The ARGUMENTS placeholder (with a leading `$`): the text after the skill name. `/dev-x`: your invocation of dev-x. Other `dev-*` skills are optional; if absent, do the step here, never skip it.

## Hard rules

1. **Never push.** Only `git commit` locally. If the user explicitly asks to push, do it as a separate confirmed step.
2. **Never amend an existing remote commit.** Always create new commits.
3. **No AI/human attribution.** Do NOT include any of the following in commit messages:
   - `Co-Authored-By: Claude ...`
   - `🤖 Generated with [Claude Code]`
   - "Generated by ...", "Authored by AI ...", or any similar trailer
4. **No `--no-verify`** unless the user explicitly asks. If a hook fails, fix the underlying issue and try again.
   **Never `SKIP=<hook>` either** — gates that CI also runs are BLOCKING
   jobs in the pipeline; skipping them locally just moves the failure
   to the MR/PR. If a full-tree hook fails on phantom errors during a
   multi-group batch, the cause may be pre-commit's unstaged-stash (the checker
   sees a Frankenstein tree) — run full-tree checks at **pre-push** or in the
   step 6 gate, not per-commit. If they fail there, the errors are real: fix them.
   If a local checker disagrees with CI, the environment has drifted — close the gap
   (e.g. install the missing extra or sync dependencies), don't skip.
5. **No `git add .` or `git add -A`.** Stage explicit paths so unintended changes (secrets, scratch files) cannot leak in.
6. **Never blanket-reset, and never hide hunks by reverting them.** `git reset HEAD` can unstage the user's work, and reverting a working file can lose it. Check the index before each group so each commit only contains what the user expects (step 3).

## Procedure

### 1. Survey

Run these in parallel:

```bash
git status --short
git diff --stat
git diff --cached --stat
git log --oneline -5
```

Read the full diff for any file you don't recognize. Note for each
changed file: which logical concern it belongs to.

### 2. Group

Cluster files by **intent**, not by directory. Each group should be a
single sentence answer to "what does this commit do?". Common groups:

| Intent | Typical files |
|---|---|
| Deployment / docker | `Dockerfile*`, `docker-compose*.yml`, `scripts/docker/`, `.env.example` |
| CI / tooling | `.github/`, `pyproject.toml`, `pytest.ini`, `requirements*.txt` |
| Hygiene / ignore | `.gitignore`, `.dockerignore`, `.pre-commit-config.yaml` |
| Docs reorg | `docs/`, root-level `*.md` moves |
| Security hardening | entrypoints, secret guards, auth code |
| Script / folder reorg | `git mv` chains under `scripts/`, `tests/` |
| Cross-reference fixes | follow-up edits triggered by a previous group's moves |

**Rules of thumb:**
- A file edit that exists *because of* another change in this batch (e.g. updating a path comment after a `git mv`) belongs in the same commit as the move it's reacting to. Same intent.
- If two unrelated hunks live in the same file, split them with `git add -p` (manually), or by staging a reviewed patch of the first hunk with `git apply --cached`. If they overlap too tightly to split, keep them together in one commit.
- Aim for 3–8 commits for a typical batch. If you're producing 12, you're slicing too thin. If you're producing 1, you're not slicing.

### 3. Stage cleanly

For each group:

```bash
git diff --cached --name-status   # is anything staged that isn't this group's?
git add -- <explicit paths>       # never -A or .
git diff --cached --name-status   # verify only intended files are staged
```

If something staged doesn't belong to this group, leave it staged: commit the
group with `git commit --only -- <paths>`, after checking every hunk in those
paths belongs to the group. If a clean split isn't possible, leave the group
uncommitted and say why. Never unstage the user's work to make a split easier.

For renames: stage **both** the old and new path so git records it as a rename, e.g.
```bash
git add OLD.md docs/new.md
```

### 4. Commit

Use a HEREDOC for the message (or a message file, where the shell has no heredoc):

```bash
git commit -m "$(cat <<'EOF'
<scope>: <imperative summary, lowercase, ≤72 chars>

<optional body — only if needed for non-obvious detail>
- bullet 1
- bullet 2
EOF
)"
```

**Message style:**
- **Subject line**: `<scope>: <imperative verb phrase>`. `<scope>` is one of `docker`, `docs`, `chore`, `scripts`, `tests`, `ci`, `feat`, `fix`, `refactor`, unless the repo has its own commit convention. Keep ≤72 chars. No trailing period.
- **Body**: omit if the subject says enough. If you do write one, use bullets for multi-thing commits, prose for single-concern detail. State *what* and *why*, never *how*.
- **No emojis** unless the user explicitly asks.
- **No mention** of AI, "Claude", "Generated with...", "Co-Authored-By", or similar.

### 5. Verify between commits

After each `git commit`:

```bash
git status --short                # confirm only the next group is left
git log --oneline -1              # confirm the message looks right
```

If a hook (pre-commit, lint, test) fails: fix the issue, **re-stage**, create a **new** commit. Never `--amend` to bypass.

### 6. CI-parity gate (MANDATORY before declaring done)

The commits exist locally — now prove they'd survive the repo's pipeline
BEFORE the user pushes. Find the gates in its CI config (`.gitlab-ci.yml`,
`.github/workflows/`, and so on), pre-commit and pre-push hooks, and contributor
docs, then run the same gates CI runs, against the full tree:

```text
<type checker>                            # must be 0 errors where it's a BLOCKING CI job
<architecture or lint gate, if any>       # no errors
<test suites covering the changed areas>
```

If the repo has no CI or gates, say so and run the tests covering the changed areas.

If a gate fails here but "looked fine" during commits: the errors are real
(commit-stage runs can be fooled by partial staging; this full-tree run is
the truth). Fix them and land a follow-up commit — never skip, never
`--no-verify`, never leave it for the pipeline to find.

### 7. Final check

When the working tree is clean (or holds only unrelated work that was already there):

```bash
git status                        # "nothing to commit, working tree clean"
git log --oneline -<N>            # show the N commits you just made
```

Surface the commit list to the user as the final summary — including the
CI-parity results (each gate's outcome, suites green), so the user knows a push
is safe.

## Anti-patterns

- ❌ One giant commit "fix everything"
- ❌ `git add -A` followed by `git commit -m "wip"`
- ❌ Commit messages like "various improvements", "stuff", "wip", "minor fixes"
- ❌ Mixing a refactor with a behavior change in the same commit
- ❌ Pushing without explicit user request
- ❌ Skipping hooks with `--no-verify` or `SKIP=<hook>` (gates CI also runs are blocking — a local skip is a deferred MR/PR failure)
- ❌ Declaring the batch done without the CI-parity gate (full-tree checks + affected suites)
- ❌ AI/human attribution trailers (Co-Authored-By, "Generated with...")

## Worked example (reference)

A batch with these pending changes:
- `Dockerfile.dev`, `docker-compose.yml`, `scripts/docker/{up.sh, down.sh, host-dev.sh}` (deployment)
- `scripts/docker/entrypoint.sh` (secret guard)
- `.dockerignore`, `.gitignore` (hygiene)
- `VISION.md → docs/vision.md` (and 3 other doc moves)
- `pytest.ini`, `py.typed`, `requirements-*.txt`, `pyproject.toml`, `.github/workflows/ci-cd.yml` (tooling)
- `scripts/tools/*` reorg into subfolders + cross-ref edits in 5 files

Splits into:

1. `docker: add multi-tenant build profiles and dev iteration helpers`
2. `docker: refuse to start with default admin secrets`
3. `chore: audit .dockerignore and .gitignore`
4. `docs: move loose root docs to docs/`
5. `chore: consolidate Python tooling into pyproject.toml`
6. `scripts: regroup tools by integration; add host-services and tests/smoke`

Six commits, each readable on its own, each leaves the tree compilable, no push.
