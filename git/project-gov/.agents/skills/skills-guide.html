01 · The workflow

From an open question to a verified change.

The main flow moves a change toward delivery. The outer loop preserves program decisions; evidence and verification send the work back wherever it needs another pass.

Read the connections in plain language
  • Core flow: brainstorm a direction → plan → implement → test → check architecture and requirements → prepare release changes when needed → commit.
  • Program loop: chart a destination, ledger, frontier, and unknowns. Work one ready ticket through its appropriate workflow; record actual resolution and unblock dependent work. A handoff alone is not a completed ticket.
  • Uncertainty: explore an unclear area with brainstorm; use dig once there is a falsifiable question worth measuring. Probe evidence can feed a broader debug investigation.
  • Support: debugging provides a cause and fix plan; refactoring improves the selected module; documentation audit repairs drift. Installation establishes local readiness before work.
  • Feedback: failed checks and verified gaps return to a focused implementation change, then rechecking. Scope determines which reviews are useful.
  • Release: bump-version prepares a consistent release diff before the release commit. Tagging, publication, and deployment follow the repository's separate procedure when requested.

These are entry points, not mandatory gates. Testing, release policy and scope come from AGENTS.md and your request.

dev-brainstorm

Explore a rough idea against the repository, compare viable framings, and recommend one direction with its trade-offs and unresolved questions.

Produces

dev-map

Chart a program spanning several plans, preserving decisions, dependencies, and unresolved areas between sessions.

Produces
A MAP.md with destination, arrival criteria, append-only decision ledger, typed frontier, and unresolved areas.

Investigate a failure04

dev-debug

Turn a vague symptom into ranked hypotheses, evidence, a supported cause, and a fix plan with checks for adjacent risks.

Produces
An investigation and fix plan, or a precise account of remaining uncertainty and the next required evidence.
In this repo
resources/work/debug/<slug>/<slug>.md
Example & details

Rank at least three falsifiable hypotheses, then confirm or rule out each one with code, logs, tests, and history. Every fix plan includes adjacent risks and a copy-paste verification recipe. You see a summary in chat before the document is written. Refinements append dated updates. Trivial fixes skip the document, structural ones hand off to a plan, and the skill never applies the fix itself.

Measure one question05

dev-dig

Run one bounded diagnostic probe to turn a surprising metric into a measured fact and a useful next question.

Produces
A recorded hypothesis, measurement, evidence, verdict, and a mandatory next probe.
In this repo
On the owning record, or an investigation in resources/work/debug/.
Example & details

Choose the cheapest measurement that could kill one hypothesis, working through the repository’s own census, trace, eval, configuration, and cost tools. Record the numbers and exact command on the owning ticket or document. Default-off instrumentation may be added while preserving behavior; fixes are separate work. Finish with confirmed, killed, or needs a bigger instrument, then name the next probe: no probe is a leaf.

Improve a module06

dev-refactor-module

Apply focused quality passes to a module or folder using the repository’s language, framework, and tooling while preserving behavior.

Produces
Scoped code improvements, a file-by-file change report, verification results, and any deferred passes.
In this repo
In a product repository, run GitNexus impact on a symbol before you change it.
Example & details

Keep edits inside the selected folder and run ten ordered passes: typing, model migration, logging, docstrings, imports, field descriptions, deduplication, error handling, configuration, and helper reuse. The passes are written for Python; other languages apply each pass’s intent, and a pass with no equivalent is marked N/A. Reuse the repository’s shared helpers before extracting new ones, and do not introduce a new configuration system.

Strengthen coverage07

dev-test-scope

Assess observable behavior in a selected code area, then add or strengthen tests that detect meaningful regressions.

Produces
New and strengthened tests, and a per-file report of functions tested, added, and enhanced.
In this repo
The tools’ tests run with py -3.12 -m unittest discover -s tests.
Example & details

Accepts a path, component description, or uncommitted changes. Inventory public functions as tested or untested, assess the quality of existing tests, then add or strengthen them. Mock external boundaries only, skip trivial getters, and fix a failing test rather than the source unless the source has a real bug. Examples use Python and pytest; other stacks use the repository’s own framework.

Check architecture08

dev-architecture-review

Review code against the repository’s documented architecture, boundaries, contracts, and conventions, with evidence for every claimed rule violation.

Produces
Source-cited findings with severity, code locations, specific corrections, and review coverage limits.
In this repo
Findings come only from VISION-RATIFIED ADRs; a known deviation is reported as known: DEV-xxx.
Example & details

Accepts a path, PR or MR reference, staged changes, or uncommitted work by default. Discover architecture documents, rules, ADRs, and lint gates first, using the bundled scanner or manual discovery. Every finding cites the rule it breaks, and the repository’s own ADR statuses, deviation register, and severity scale apply. Here, DRAFT ADRs give advisory notes, new deviations are proposed rather than written, and the severity scale is the one in AGENTS.md. This is a review, not a fix.

/dev-architecture-review --staged

Close the spec loop09

dev-spec-verify

Check a plan, PRD, audit, or written requirement against implementation using atomic claims and evidence-backed verdicts.

Produces
A claim-by-claim verdict table, a focused real-gaps list, and summary totals.
In this repo
Against the PRD mirror in prd/ or a plan; the report goes to resources/audits/.
Example & details

Exactly one verdict per atomic claim: IMPLEMENTED, PARTIAL, MISSING, or DEFERRED. Better-than-spec is not a gap. Every verdict cites evidence, and MISSING cites where it was expected. Only the specification can defer a claim. The audit recommends no new work and never edits the specification; updating STATUS.md is your call.

Reconcile documentation10

dev-doc-audit

Check living documentation against current code, verify claims and links, identify coverage gaps, and make scoped repairs.

Produces
Corrected documentation plus evidence-backed findings, verification results, deferred gaps, and scope limits.
In this repo
Report in resources/audits/. The PRD mirror is generated: it is never edited.
Example & details

Default invocation runs three audit passes, plans five workstreams, and lands source-of-truth fixes first so later docs can cite them. Use --no-write for the plan only, or --source-of-truth-only for contributor entry points, architecture docs, and rules. Scope by path or topic when useful. Patch rather than rewrite, verify every claim against current code, and keep new files under about 400 lines.

Commit coherent changes11

dev-group-and-commit

Organize authorized local changes into small, logical commits with concise messages while preserving unrelated work and existing staging.

Produces
Local commits, their hashes and subjects, completed checks, and a report of remaining changes.
In this repo
Only when asked, once the tests pass. It never pushes.
Example & details

Group changes by intent, usually three to eight commits, and stage explicit paths or reviewed patches. Existing staging is never reset, and hunks are never hidden by reverting them. The batch is not done until a mandatory CI-parity gate passes: the same gates CI runs, against the full tree. Hooks are never skipped, messages carry no AI attribution, and pushing is a separate, explicitly requested step.

/dev-group-and-commit

Prepare a release12

dev-bump-version

Move the version forward one validated step, refusing jumps and backward moves, and keep the changelog and every version file in agreement.

Produces
A reviewable release diff and a suggested commit. It never commits, tags, or pushes.
In this repo
The version is in pyproject.toml, with no documented cadence: one patch per request.
Example & details

Discover the version files, changelog, generator, and any documented cadence. With a cadence, it takes every due window and rejects other targets with a message showing the natural next version; now forces a hotfix. With none, it bumps one patch on request, and minor or major only when you name them. Existing changelog entries are never re-dated.

Prepare the checkout13

dev-install

Discover a repository’s development setup, bootstrap the required local environment, and verify its documented readiness checks.

Produces
A verified local setup or readiness audit, with a rollback summary of everything installed.
In this repo
Python 3.12+, pandoc 3+ and git.
Example & details

Full setup audits prerequisites, asks before every install with a gentle option, an alternative, and a skip path, walks .env section by section, starts the documented local target, and smoke-tests it. 03 · Practical recipes

A few ways to put them together.

Use a recipe as a starting point. Linked steps open the relevant skill; plain steps show implementation work, intermediate outcomes, or handoffs.

01 Build a feature

Explore when the direction is open, then plan a useful increment. Check both its behavior and its fit with the design.

  1. brainstorm
  2. plan / refine
  3. implement
  4. test-scope
  5. architecture-review
  6. spec-verify
  7. doc-audit, if needed
  8. group-and-commit

02 Steer a larger program

Keep decisions across plans and sessions. A handoff stays open until the work produces the evidence needed to resolve it.

  1. map · chart
  2. map · work
  3. resolve one ready ticket
  4. record + unblock

03 Investigate a bug

Establish the cause and adjacent risks first. Then request the fix and verify the behavior that originally failed.

  1. debug
  2. implement the fix
  3. test-scope
  4. group-and-commit

04 Explain a surprising metric

Turn a suspicion into one falsifiable measurement. A negative result is useful: it eliminates an explanation.

  1. dig
  2. record the verdict
  3. next probe
  4. implement if warranted

05 Bring the docs up to date

The audit includes scoped repairs. Add --no-write for a findings-only pass, or name a topic to narrow it.

  1. doc-audit
  2. inspect the diff
  3. group-and-commit

06 Prepare a release

Follow the repository’s version model. Preparation updates the release diff; tagging and publication follow when requested.

  1. bump-version
  2. validate the release diff
  3. group-and-commit

04 · Use them here

One folder. Every agent tool.

The skills are generic; this repository’s conventions live in AGENTS.md. Each skill reads them there: where its output lands, which ADRs bind, how severe a finding is.

  1. Open the repository in your agent.

    Codex, Copilot and other AGENTS.md readers load the skills from .agents/skills/ directly. Any other agent can read .agents/skills/<name>/SKILL.md as plain instructions.

  2. Claude Code: link them once.

    Claude Code reads only .claude/skills/, which is gitignored. Run py -3.12 tools/skills/link.py after cloning, and again after a skill is added or removed. A second run changes nothing.

  3. Give the agent a concrete task.

    Invoke a skill with a path, a symptom or a goal. Planning and setup skills ask their questions, then wait for your approval before they write a document or install anything. Nothing is committed or pushed unless you ask.

05 · Why this works

A workflow that remembers its reasoning.

The useful part travels with you: explicit decisions, evidence, and focused work. The project-specific rules stay with the project.

01 / CONTEXTDiscover before prescribing.

Architecture, frameworks, tools, and release policy are inputs. A skill reads them instead of imposing another repository’s conventions.

02 / CONTINUITYKeep the decision history.

Maps and plans retain accepted decisions. A reversal appends a superseding choice; brainstorm and debug refinements preserve the earlier evidence.

03 / VERIFICATIONCheck the code against its intent.

Architecture review cites ratified ADRs and repository rules. Spec verification checks atomic requirements. An equivalent implementation is valid; unavailable evidence stays explicit.

04 / PROPORTIONUse the process the change needs.

Choose meaningful behavioral checks and coherent increments. A typo does not need a program map, and an obvious fix does not need a large investigation.

05 / UNCERTAINTYMake the unknowns visible.

Separate settled choices from open questions, blockers, and areas that need exploration. A falsified probe or an inconclusive investigation is useful evidence.

06 / SCOPELet the user set the pace.

Each skill stops at its own output: an approved plan, a findings report, a diff. Implementation, commits, and pushes are separate steps you trigger.

06 · Keep them current

Improve them upstream. Sync them here.

The dev-* skills belong to the Dev Skills repository. Improve them there, pull the change in, and keep this project’s rules in AGENTS.md.

Check, sync, link, test.

The upstream is [skills] upstream in workspace.toml, or --from a local checkout. Each dev-* folder is replaced whole.

py -3.12 tools/skills/sync_upstream.py --check py -3.12 tools/skills/sync_upstream.py py -3.12 tools/skills/link.py py -3.12 -m unittest discover -s tests

--check changes nothing and exits 1 when a skill differs from the upstream. On macOS and Linux, run python3 instead of py -3.12.

Read the skills section of AGENTS.md ↗

Never edit a dev-* skill here.

The next sync overwrites it. Put the project’s rule in AGENTS.md instead, the way its “Architecture review” and “Where things land” sections do.

Only dev-* folders move.

The sync never touches gov-* or local-* skills. A dev-* skill the upstream no longer has is listed, not deleted: remove it by hand, with its row in AGENTS.md, since the tests require every skill to be listed.

Keep this guide aligned.

When a sync changes a skill, update its card and examples here. The linked SKILL.md files define behavior; this page explains how to use it.
